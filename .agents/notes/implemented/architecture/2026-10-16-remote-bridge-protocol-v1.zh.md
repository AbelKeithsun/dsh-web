# Agent Note: 远程桥协议 v1 是与传输解耦的原生客户端面

Status: implemented

同级面的决策：[远程控制复用官方界面](2026-08-29-remote-control-reuses-official-ui.md) 拥有浏览器路径——配对设备 cookie 与受门禁的 `/remote` 通道。本 note 拥有第二条面：为原生客户端准备的、协议形状且不带 cookie 的路径。

## Problem

`dsh-remote-web-ui` 靠配对浏览器发布手机面：设备拿到 cookie，之后每次调用都走 `/remote` 通道，而该通道用进程自身的浏览器凭据重新签发。对浏览器而言这是正确的形状——它白拿了官方 UI、移动适配层与设置桥。对没有浏览器、没有 cookie 罐、也没有 Web GUI 包体的原生客户端而言，这是错误的形状：iOS App 得先模拟一个浏览器会话，而且照样继承网页的失效模式。

两条约束决定了这里「原生客户端」只能是什么样。其一，宿主没有为此准备的官方 HTTP API：从远程 origin 直接打 `/api`，受制于宿主围栏恰好信任什么，而把产品建在其上的插件会把 SDK cohort 的端点名与宿主自身的鉴权变成自己的版本耦合依赖。其二，浏览器凭据本身无法跨中继回放：它与浏览器访问过的确切 `host:port` 绑定，且没有 loopback 豁免，因此代理重发到 `127.0.0.1` 会被拒——正是 `dsh-remote-web-ui` 不得不自行兑换 launch token 才绕开的那个缺陷。

所以原生客户端需要一种宿主本来没有的传输，以及自己的访问控制。缺的是一个决策：这条面是什么、如何鉴权、与浏览器那条面是什么关系。

## Decision

- **桥是独立包，协议 v1 是独立契约。** `@linxin666/dsh-remote-bridge` 是同一插件行承载的两个半区（`packages/dsh-remote-bridge`）：宿主半区发布一条精确的 WebSocket upgrade 路由 `/ios/v1` 与一条精确的 HTTP 路由 `/remote-bridge/pair/token`，而同一行声明的浏览器半区（`dsh.client` -> `exports["./client"]`）再加一个侧栏底部的配对面板。协议是一套 JSON 信封——`{"t":"req","id","m","p"}`、`{"t":"res","id","ok","r"|"e"}`、`{"t":"ev","seq","m","p"}`、`{"t":"ping"|"pong","ts"}`——一条消息一个文本帧；方法层不出现 HTTP、cookie 或浏览器会话，因此同一套信封可以原样跑在 loopback socket、局域网绑定或被中继的 origin 上。
- **桥在进程内消费宿主。** 会话工作走 `ctx.typertGateway`（一元调用用 `invoke`，`session/follow` 用 `stream`），只以 gateway 的 `error.code` 作为失败判别，并对服务激活窗口使用家族既有的有界重试。权限请求在同一进程内监听 `ctx.on('approval/request')` 作答——绝不走 `$events`/`$events/result`——而无人应答的审批会被归一为 `unavailable`，宿主按拒绝处理，因此沉默的手机永远不等于同意。
- **每次网关调用都以同一个进程内 owner peer 发言，且只在桥自己的配对门禁之后被用到。** 自 SDK 0.2.1 起 `InvokeRemoteRequest.peer` 必填，而鉴权层只读 `peer.principal`；桥在挂载时于 `core/owner-peer.ts` 铸造单个 owner peer（`{kind:'owner'}`、`interactions:'none'`），绑定插件 fiber、`dispose()` 幂等，并挂到每一次 `invoke` 与 `stream` 上。这个完全控制声明安全的原因与 0.2.1 之前那种隐式特权相同：通向它的路径都要过桥的配对检查——分发在任何网关调用存在之前即以 `unpaired` 作答，而那三个未配对方法从不调用网关——且客户端帧的任何字段都不会被读进 peer，因此客户端无法自报 principal。`interactions:'none'` 保证不碰宿主转发事件：审批经桥自己的 `approval/request` 认领与协议自有事件抵达设备，而不是经 Typert 转发事件订阅。
- **桥自签 bootstrap token。** 仅 loopback 可达的 `GET /remote-bridge/pair/token` 把一枚 32 字节、30 秒有效的一次性密钥交给操作者；`pair.begin` 花掉它并签发 nonce；`pair.finish` 用所给 P-256 SPKI 验证对该 nonce 的原始 64 字节 ES256 签名，然后在 `$DSH_HOME/remote-bridge/devices.json` 落一条名册条目——公钥、SHA-256 指纹、时间戳（目录 0700、文件 0600、临时文件加原子 rename）。设备令牌本身是 32 随机字节，只保留其 SHA-256 哈希。`dsh-remote-web-ui` 不被改动：它的配对服务继续为浏览器路径签发 cookie，两份名册是两个文件，吊销互不相干。
- **浏览器半区渲染那枚 token，且从不消耗它。** 面板注册进官方 `sidebar.footer.action` 座位——ui-sidebar 声明的那个列表槽位，`dsh-remote-web-ui` 的手机触发器与 `dsh-update` 的更新器已经占用它——用同源请求读同一条仅 loopback 门禁的路由，并把密钥以 `qrcode.react` 二维码加旁边的明文呈现，配 30 秒倒计时与「重新取码」动作。二维码里装的只有裸 token：那里若放 URL 或 JSON，手机端自己的解析器会把 origin 改写成这台机器的 loopback 地址，而那恰恰是手机唯一够不到的地址。`403` 与网络失败各自渲染成有名字的状态，绝不呈现为一块沉默的面板。面板不能签发设备令牌、不能消耗配对码、不能列名册、不能吊销设备，也不新增任何 wire 面。
- **一条授权规则，在分发之前检查。** 设备令牌缺失、未知或已吊销的连接只能调三个方法（`hello`、`pair.begin`、`pair.finish`），其余一律回 `unpaired`。设备令牌随 upgrade 以 `Authorization: Bearer` 携带，也给无法设置握手 header 的客户端留了 `?token=`；比对先对两侧取哈希，再比等长摘要。
- **不做增量补发。** 连接的 event `seq` 自 1 起，给的是该连接收到的东西编号；发现跳号或重连的客户端调 `session.snapshot` 拿完整基线。`session.snapshot` 打开宿主 `session/follow` 流并保持它作为本连接的订阅，因此增量无需轮询即到达；而快照的 `lastSeq` 是宿主游标——与 `seq` 是两个计数器，协议从不比较二者。
- **一帧 10 MiB，且客户端可以要求一份它真能渲染的基线。** 上限是一个常量（`MAX_FRAME_BYTES` = 10 MiB），接收判定、快照拟合、`frame-too-large` 文案与出站事件丢弃都读它，因此这个数字不会被写第二遍；它从 256 KiB 提高，是因为手机的基线就是一整个会话历史压在一帧里。但只提上限，等于把「被拒绝」换成「打开得极慢」：基线里的大头是客户端根本不渲染的持久记录——单个回合内部的 `system/message` 与 `request/header` 段落，动辄 150 KB 以上。于是 `hello` 的 `cap` 数组现在会被读取，声明 `session.snapshot.trim.v1` 的客户端拿到的基线在每个回合内部被裁到它能渲染的四种 entry（`user/message`、`assistant/message`、`tool/call`、`tool/result`）；一个回合的 entry 若全是记账记录，该回合仍保留为 `entries` 为空的回合；每个回合级字段、回合列表与 `lastSeq` 都保持投影自己的取值。能力是公告而非协商：未知名字、读不懂的 `cap` 与缺失的键都被忽略，什么都不声明的客户端——该能力出现之前写下的所有客户端——逐字节拿到协议 v1 一直以来提供的基线。裁剪先于帧预算：先裁 entry，再丢最旧的整回合，之后才轮到 `snapshot-too-large` 作答。
- **被委派的子会话通过持久父地址寻址，历史按 entry 分页。** `session/follow` 与 `session/page` 收的是 `SessionAddress`，而把一个子会话当作普通会话来问，宿主会拒绝：`session/agent-busy`——"subagent Sessions require their durable parent address"。正是这条拒绝，让某台手机 828 行名册里的 457 行、对那些明明握着完整日志的会话回 `snapshot-unavailable`：桥对每个 id 都发 `{kind:'session'}`，并把宿主自己的诊断抹成一句读起来像临时故障的泛泛失败。现在桥只对这一个会话改用 `{kind:'subagent', parentSessionId, childSessionId, mode:'unknown'}` 重试，父 id 取自名册——唯一携带谱系的端点——且每个连接至多读一次；其余任何失败都带着宿主自己的错误码穿过，不再被吞掉。`mode` 恒为 `unknown`：宿主会把声明出来的 mode 与子会话描述符比对，而对任何子会话都接受 `unknown`，且桥在调用前读不到子会话的 mode。同一处修复让 `session.history` 对这些会话也生效：它从持久 `seq` 水位按 **entry** 往回分页，默认每页 512 KiB，允许一个回合的 entry 跨页而该回合保留自己的字段，让比整页预算还大的单条 entry 独占一页而不是被拒，并且是绝不打开、丢弃或改指订阅的纯读。
- **第二个能力给首屏本身加上预算。** 把 `session.history` 往回分页，并没有切分首屏：打开一个活跃会话仍然一次交付整个 3.3 MB 开帧窗口，所以「大会话像小会话一样秒开」当时并不成立。`session.snapshot.page.v1` 让 `session.snapshot` 改回最新一页，用的是 history 那同一套按 entry 的切片，并按 `maxBytes`（默认 512 KiB）衡量，因此首屏与其后每一页都出自同一条代码路径，不可能互相矛盾。能力门控正是让它不构成回归的原因：不声明的客户端逐字节拿到整个窗口；声明的客户端额外拿到 `hasMore`，以及一个恰好等于它自己最旧那条 entry 的 `seq` 的游标——正是 `session.history` 的 `before` 所取的值，所以不再有字段重述它。`snapshot-too-large` 不会再回给声明了该能力的连接，因为比预算还大的 entry 会独占一页而不是被拒绝。
- **一条消息会说明它从哪来，而一个被派生出来的子会话是它自己的 delta。** 协议 v1 一直携带内容却不携带来源：无论人打的、子会话转述的、还是宿主注入的运行时上下文，每条持久 `user/message` 都变成同一个 `user-message` delta，而"某个 agent 起了一个子会话"这件事在线路上完全没有公告。本通道落地时 `hello` 回 `minor:2` 并公告 `capabilities`——本桥当时服务的四个：`session.snapshot.trim.v1`、`session.snapshot.page.v1`、`questions.v1`、`subagent.thread.v1`（今天是七个、`minor:5`，见最后一条）。插件注册的能力不在其中：桥不是它的作者，客户端照旧从插件自己的文档得知它。`user-message` delta 与快照里的 `user/message` entry 现在带一个可选的 `actor`，机械地取自持久 `source` 记录：`user` 与 `user-approval` 是 `human`；`agent-message` 与 `subagent-settled` 是 `agent`，并带上发送方的会话 id；其余任何来源种类都是 `system`，原文照抄——一条消息不会因为携带了本契约没分类过的来源就被丢弃，而 source 里读不出种类的错误事件干脆不带 `actor`，而不是猜一个。`actor` 不受能力门控：它是可选键，从不读它的客户端直接忽略。`subagent` delta 由 `subagent.thread.v1` 门控，从持久 `subagent/catalog` 事件取 `{childId, label?, mode?, callId?}`，并且只在同一个 turn 与 step 只发过一条 `tool/call` 时才把锚点接到派生它的那次调用上；一步发过两条、或同一条调用已经挂过另一个 child 时，锚点一律省略而不是猜——`callId` 猜错会把手机上的线程挂到错的卡片上。
- **跟随一个被委派的子会话需要授权，而授权本身决定谁可被读取。** 读子会话自己的日志，正是"放宽一条地址裁定"可能变成"任意会话读取通道"的那一处，因此规则用"本连接已经可以读哪些会话"来表述：名册列出的普通会话、以及本连接已经打开过的任何会话都可跟随；被委派的子会话只有它名册行上的 `parentSessionId` 解析进这个集合时才可跟随，而子会话自己那一行永远不构成自我授权——否则一次被拒的读取就会教会这个连接在下一次重试里读它。父会话解析不出来的子会话在任何 follow 流打开之前就回 `session-not-followable`；而名册完全不认识的 id 维持旧路径，由宿主自己对它作答。这条裁定要求在做第一次尝试之前就知道谱系，所以名册在那时读：被名册指明父的子会话直接用委派地址寻址，而那次读取没能解析出父时，仍由宿主的 `session/agent-busy` 拒绝驱动唯一一次重试。
- **中继无需改动。** 桥搭在实例本来就发布的那个 origin 上：`market/worker/src/relay.js` 查出隧道目标、只重写 `Host` header、原样返回 origin 的响应，而 WebSocket upgrade 走同一跳，因为 Workers 运行时会把携带 `Upgrade` 请求且 body 为空的 `fetch` 升级为 WebSocket。把 token 端点挡在公网 origin 之外的是 loopback 门禁，不是中继。- **名册带上宿主自己的会话元数据，标题在本进程内读。** `session.list` 除重发手机用来分组与命名的摘要字段——`cwd`、`parentSessionId`、`origin`——以及 `blank` 之外，还从 workspace registry 的唯一归档集补上 `archived`；每个可选键只在本次进程确实能回答时才出现，因此读不到归档集的桥省略该键，而不是回 `false`。`session.titles` 用 `ctx.sessionTitle.get` 读 `ctx.sessions` 活跃持有的会话，回答一批最多 100 个 id——绝不为每个会话各开一条 follow 流（名册里空标题的老代价正来自此）——并把每个已解析的标题缓存 10 秒。缓存按时间失效而不是按事件失效：标题变更是 `session/title` 这条*日志*事件，背后没有 cordis 事件；做失效钩子等于给每个活跃会话挂一个监听器，而 TTL 把陈旧度限住（重命名最多 10 秒后才可见），且每次批量调用本身就是一次刷新。两个服务都通过 `ctx.get` 以可选的结构化 face 访问，而不进 `inject`：把它们列为必需会让标题或工作区插件缺位时整个桥一起倒下；服务未挂载时，一个 id 回 `""`，一个键被省略。
- **后台任务只读发布，用宿主自己的两个 scope，且只发给问过它的客户端。** `hello` 现在回 `minor:3` 并公告 `jobs.v1`；其背后 `jobs.list` 回 `{sessionId?, scope, jobs}`，`jobs.changed` 载荷是**同一个盒子**。桥读的是 `ctx.jobs`——`job` Remote 命名空间本身就是它的一个投影——因此没有第二份存储、没有轮询、也没有自己的状态词表：每一行是 `{id, kind, status, label, ownerSessionId?, startedAt, finishedAt?}`，逐字段取自宿主的 `JobView`，而宿主的 `output`（环偏移与 spill 路径）、`progress`、`detail`、`outputLimitBytes` 一律不上线。任务表在宿主侧按 owner 设防（`JobRegistry.list(caller?: SessionId)`）：点一个会话，得到该会话自己的任务加所有无主任务；不点会话，只得到无主任务；宿主没有全局表可发。于是本方法收可选的 `sessionId`，有则以 `scope:'session'` 回显它，无则回 `scope:'unowned'` 且不带会话键。桥**不**把两者折成一个假全局视图：那要么是把 N 个设防读聚合起来，要么是第二份事实源；诚实的话就是宿主自己的话——任务归会话所有，`unowned` 不是「全部」，两个都想要的客户端调两次。变更检测用宿主 registry 自己的事件流，只取生命周期提交：`output` 追加不动任何一行，在这一层就被丢弃，所以这条通道永远不会退化成「每个输出字节一帧」。一波提交由 100 ms 窗口折叠——正是 job controller 自己给 `observeFlushMs` 用的默认值——窗口到期后整集重读，若投影与该连接上一次收到的帧完全相同就不发。订阅是 `jobs.list` 换来的：声明了 `jobs.v1` 却一次都没列过 scope 的连接收不到任何任务帧，也不让 registry 多一次读——这正是「N 个打开着的会话变成 N 份集合往一个什么都没问的手机上推」的拦阻所在。订阅随连接结束，而 registry 上的事件订阅随最后一个订阅者结束。
- **已握着一份集合的客户端只收差值，而差值由桥算。** `hello` 现在回 `minor:4` 并公告 `delta.v1`；它背后 `session.list` 与 `board.snapshot` 接受一个可选的不透明 `since` 令牌，回两种形状之一——`{mode:"reset", token, …}` 带与从前逐字相同的整份身体，或 `{mode:"delta", token, …changed, removed}` 只带动了的部分。这件事只能在桥里算：桥本来就按连接持着它上一次发出的那一份，而宿主每次照旧回答完整集合——所以省下的是桥与手机之间的字节，从来不是宿主 API 的变化。一行算"变了"的判据是**整行的序列化结果**与上一次不同，而不是某个时间戳动了：宿主的 `updatedAt` 不是 `agentRunning`、`blank`、`archived` 或任务 `column` 的变更信号。`removed` 一定会发：一个本连接被发过、这次宿主不再列出的 id 进 `removed`，因为静默丢掉一行比一次 reset 更糟。每条连接最多保留它最后一份完整集合——名册 5000 行、看板 2000 个任务——越过上限即回 `reset` 且令牌为空，一部手机绝不能钉住宿主状态的无界副本；`changed` 超过全部行数的 60% 时也回 `reset`，因为过了这个比例增量本身就带着身体的大部分，多出来的两个键只是让它更大。不是本连接自己发出的令牌——别的连接的、上一次启动的、更早一次应答的、或任何垃圾串——一律回 `reset`：基底错了答案就是错的，只有这个窗口最后发出的那一份才允许被当作差值基底。从未声明 `delta.v1` 的客户端收到的是今天的身体加上可忽略的 `mode` 与 `token` 两个键，且不为它保留任何副本，因此这条通道之前写的每个客户端逐字节停在原地。窗口是连接对象上的一个字段（`core/delta.ts`），随连接一起消失；看板插件通过扩展缝（`declares` 与按连接的 `deltas` 座位）借用同一套机制，而不是把一份被协议钉死一次的规则抄第二份。`board.snapshot` 的 reset 把宿主快照逐字保留在 `snapshot` 下——那是所有既有客户端读的东西——并在旁边发布 `revision` 与 `tasks`，于是支持增量的客户端在两种形状下解析同一套字段，而老客户端解析它一直解析的那套。
- **已归档的会话根本不在名册上。** `hello` 回 `minor:5` 并公告 `session.list.omit-archived.v1`——这是这里唯一不协商任何东西的能力，因为省下的字节属于桥而不属于某个客户端的版本：手机一收到就把每一行已归档会话藏起来，因此一份 935 行的参照名册为 346 行、212,426 字节中的 76,608 字节（36%）付了钱，而这些行从来没有客户端渲染过。归档集本来就在每次列出时读一次、用于填该行的 `archived` 标记；现在同一次读取在构造该行之前跳过已归档会话，因此它的任何字段都不会被读，也没有任何东西穿到线路上。不变的部分：该键仍留在 schema 里，存活行携带 `archived: false`；本进程读不到归档集时仍然一行都不丢、仍然省略该键；谱系仍然来自每行自己的 `parentSessionId`，因此已归档父会话的活跃子会话仍带着那个父 id 被列出。名册同时也是 delta 窗口做差分的那一集，所以这两种迁移都不需要特例：两次列出之间被归档的会话出现在 `removed` 里，被恢复的出现在 `changed` 里，与一行停止存在或开始存在的走法完全相同。唯一被收窄的是跟随闸门——授权一个会话的是名册，因此已归档父会话的子会话现在回 `session-not-followable`，直到父被恢复；在那台参照宿主上这次收窄没有任何实例（改动当时已归档父会话的活跃子会话为 0），所以选择接受这条规则，而不是靠授权一个名册不再点名的 id 把它买回来。

## Alternatives considered

- **跨中继回放浏览器凭据。** 依同级 note 已落地的证据否决：宿主浏览器鉴权 cookie 与浏览器访问过的 `host:port` 绑定且没有 loopback 豁免，代理重发到 `127.0.0.1` 会被拒；`dsh-remote-web-ui` 之所以能转发调用，是因为它自行兑换过一次 launch token 并持有活着的配对设备 cookie。原生客户端两者皆无，因此这条路会迫使桥自造并持有浏览器会话——为一段用户从未打开的会话建一个凭据库。
- **给 `dsh-remote-web-ui` 加一个签发方法。** 否决：那会把两个包的生命周期绑在一起，让一条面的鉴权依赖另一条的配置与名册格式。桥的全部意义在于原生客户端不需要安装浏览器插件；同级 note 自己的边界是浏览器通道用进程凭据重发调用——那道缝不能变成通用签发器。
- **建立在官方 `/api` HTTP 面之上。** 否决：它把宿主自身的鉴权与 SDK cohort 的端点名变成桥的兼容性契约。同级 note 记录到本 cohort 上运行时并不发出 `api/gate` 缝，因此从远程 origin 直接打 `/api` 只受宿主围栏加上浏览器已兑换的那份 cookie governing——一种桥既说不清也管不住的信任姿态。
- **复用浏览器通道的 WebSocket（`/remote/api/remote.mux`）当传输。** 否决：那条 socket 是官方客户端多路复用的 Typert 连接，代理它等于把第二套协议塞进一条门禁按「已配对浏览器」定义的通道里。桥用自己那套信封，对只懂这套信封的客户端讲话。
- **把配对面板放进 `dsh-remote-web-ui`。** 否决：那个包的面板签发的是浏览器路径自己的配对链接，其凭据是配对设备 cookie——另一种密钥，生命期不同，背后的名册也不同。把本包的一次性 token 渲染到那里，会迫使两份名册与两条吊销流程保持一致，而上面划出的包边界存在的意义正是避免这种耦合；让同一侧栏座位多一个占用者，两条面就能并排放着而互不共享状态。把面板留在本包内，也让原生路径在 `dsh-remote-web-ui` 缺席时依然可用，而那正是当初造出这个桥要保住的性质。
- **缓存 delta 让重连可以增量续传。** 否决：那会把桥变成一份自带保留策略与投递保证的持久日志，而它服务的客户端群体一次完整基线调用就能恢复。snapshot 路径本就存在，也是诚实的恢复机制。
- **像 `dsh-session-log-export` 那样自己读持久化日志。** 在地址修复之后否决，因为地址修复已经消除了这个需要：解析 `session.v4.jsonl.zstd` 会让桥去拥有一套本属于宿主的压缩格式与磁盘布局，会让客户端拿到与实时流对进行中回合不一致的第二份事实源，而且换不到持久地址给不了的东西——委派地址就是通过普通会话所用的那条 follow 流，把子会话的整份日志取回来。
- **新增一个 `subagent.events` 方法，或一个 `subagent.*` 主题，承载子会话自己的过程事件。** 否决：父流本来就是桥在跟随的持久日志，子会话的出现只是手机已订阅的那条流里的一条事件——再加一个方法意味着多一条要打开、分页、关闭、授权的订阅，多一个要推进的游标，还有第二处回答"这个子会话还在跑吗"。线路上只加一种 delta；子会话的内部通过本来就存在的那条 follow 流读取。
- **把子会话的增量镜像进父流。** 否决：那会让父会话的日志成为另一个会话内容的权威，把两个会话的 turn 与 step 计数器塞进同一条 delta 流（客户端再也分不清一条 `turn-end` 属于哪个会话），并让一个会话的帧预算乘以子会话个数——无论中继那一跳还是客户端的单条订阅都不是按这个规模设计的。展开的线程订阅子会话，拿到的是任何会话都给的那套帧；收起时零成本。
- **对一个已配对客户端点名的任何会话 id 都放行跟随。** 否决：配对授权的是"你能用这台宿主"，不是"帧里写哪个 id 就读哪个"，而父会话无人解析的子会话 id，恰恰就是这道闸门要挡住的读取通道。放宽的那一格是有意做窄的——只在调用方已被授权的会话下面一层——并且只沿着调用方真正走过的路径生长。
- **用宿主自己的 `session/page` 来实现 `session.history`。** 考虑过，最终否决，改为对开帧基线分页。`session/page` 数的是 `maxMessages` 而不是字节，512 KiB 的分页预算仍然要由桥来执行；它需要的 `throughSeq` 只有 follow 开帧才提供；而它返回的记录可能从一个回合中间开始，靠它们重建回合外壳，就只能编造或省略该回合自己的 `seq`、`endSeq` 与 `reason`。开帧基线是唯一已经带着这些字段的来源，这也正是一页与一次快照永远不会互相矛盾的原因。
- **改为发布 `job/list` 那条 Remote 流，而不是读 registry。** 否决：`JobListRequest.sessionId` 必填，那条端点只服务「一个会话的设防集合」，完全服务不了 unowned scope——那里没有会话可点。读 `ctx.jobs` 用一道缝、同一个权威就服务了两个 scope；另一条路要么是两条缝配两套订阅模型，要么是塞一个合成会话 id，而「它等价于无主」这件事宿主并没有写进契约。
- **跨会话报一个全局「N 个后台任务」。** 否决：宿主没有这个视图——它两个读都是按 owner 设防的——这个数字只能由桥从 N 个设防读拼出来，而一个没人权威计算过的数字，正是这条通道存在要避免的第二份事实源。手机显示它问过的那个 scope 的计数，要两个就调两次。

- **让宿主算差值。** 否决：宿主根本没有「按连接」这个概念——名册与看板是对任何来问的人作答——让它当差分者，等于把桥的连接账本交给一个并不持有它的服务，还要教两个宿主 API 一套它们现在完全不知道的线路形状。桥是唯一已经握着「上一次发了什么」的那一层。
- **在客户端做差，反正它握着上一份身体。** 按算术否决：客户端要把整份身体下载下来才能做差，而那恰好就是要省掉的开销。而且没有在手机上保留上一份完整集合就做不出 `removed`，那笔内存正是增量想省的。
- **把看板的增量窗口放在看板插件里、按连接 id 索引。** 设计阶段试过后否决：释放一条断开连接的状态需要在插件里再来一套带过期的注册表，而且两个包会各自持有一份 §15 只钉一次的令牌与容量规则。扩展缝改为交给插件 `declares` 与连接自己的 `deltas` 座位，于是机制与其生命周期归桥，看板的词表仍归看板。
- **只要客户端发来任何它被发过的令牌就回增量，哪怕更早的也接受。** 否决：只保留最后一份，更早的令牌指向一个已经不存在的基底，答案只能是对着错的集合做差、或把发过的每一份都留着。回 reset 是诚实的答案，同时也是恢复路径。
- **把省略放在 `session.list.omit-archived.v1` 后面，让什么都不声明的客户端继续收到完整名册。** 否决：能力是公告而非协商，已归档行的字节无论谁问都要付——较老的客户端先付钱再把这些行过滤掉，所以这道闸门只保留成本，只保住「看得到没有 UI 渲染的行」这件事。反过来公告这个事实，客户端就能自己去掉过滤器，而线路不必依赖客户端的版本。
- **继续跳过该行，但把被跳过的 id 加进授权，让已归档父会话的子会话仍可跟随。** 否决：授权一个会话的是名册，把一个名册不再点名的会话重新放进来，会让跟随闸门为没有任何端点发布的 id 作答，而已归档会话会沿着名册不再展示的路径继续可读。子会话在两种做法下都保住谱系，需要父的客户端把父恢复即可。

## Consequences

- 现在有两条远程面、两套互不依赖的访问控制：浏览器路径（配对 cookie、`/remote` 通道、`dsh-remote-web-ui` 的名册）与原生路径（设备令牌、`/ios/v1`、桥自己的名册）。吊销其一不吊销其二，这正是有意的分离——也是两个包的 README 各自陈述自己安全模型的原因。
- 本包现在在宿主半区旁边多了一个浏览器半区，方向是单向的：浏览器半区可以读配对路由并渲染它，不能签发、消耗、列出或吊销任何东西。它唯一的 wire 调用，是对一条浏览器配对路径从不提供的路由发起同源 `GET`。
- 桥现在除了 wire 格式还拥有 UI 文案：面板注册了 `remote-bridge` locale 命名空间，并占用 Web GUI 侧栏底部的一个座位，因此它的触发器加入家族的底部行，文案遵循仓库的 zh/en 字典纪律。
- 协议 v1 的方法集冻结为九个客户端方法加一个审批回复：`session.titles` 与 `session.history` 加入了名册、快照、发言与中断这几条方法；桥可能调用的每个 DSH 端点的 wire 布局集中在一张表里（`src/core/wire.ts`），其中还包含三个尚无方法暴露的端点。新方法若把某个参数名写错，会在 gateway 处以 `arguments-invalid` 失败，而不是静默调错形状。子代理线程保持这个数目：它加了一种 delta 与一个可选对象，没有加方法。
- **子会话这道闸门比它生长于其上的地址修复更窄。** 父会话没有任何名册行可解析的被委派子会话，过去是能读的——follow 流只需要子会话自己那一行上的父 id；现在它回 `session-not-followable` 且不打开任何流。客户端把它渲染成解释而不是可重试的失败，而这个代价是有意的：谱系只来自宿主名册，绝不来自帧；名册在每个连接第一次尝试之前读一次；可读集合只沿调用方真正走过的路径、一层一层地生长。
- 桥自己拥有一份持久格式：`$DSH_HOME/remote-bridge/devices.json`。它的形状从上线那天起就是兼容性面；损坏的文件被隔离待查而不是被静默清零，因此「解析失败的名册」永远不会被误当成「没有设备的名册」。
- 丢掉设备令牌的客户端用一枚新的 bootstrap token 重新配对——这是常规恢复路径而非异常路径。整个流程里没有任何一步需要手工改名册。
- token 端点只能从本机触达，同一条链接会写进宿主日志，而配对码本身渲染在配对面板里；那行日志与屏幕上那串码在其 30 秒生命期内都是活着的密钥，README 把它们写在操作者会读到的地方。
- 任务通道只加一个方法、一个主题、一个能力名，不碰任何既有帧：`jobs.list` 是冻结方法集里的第十七项，老客户端从不调它、也收不到 `jobs.changed`（它们根本不会被订阅），而新客户端在老 host 上看到 `capabilities` 里没有 `jobs.v1`，必须把这件事渲染成「不知道」，绝不能渲染成「零个后台任务」。两件写成路径的事有意留在界外：`job.kill` 需要自己的审批故事，`job/follow` 的输出流会给一条只需要计数的面加上字节游标、`lossy` 标记与环形保留。
- 对每个客户端都变短的协议 v1 响应体只有名册本身，而不只是对那些声明了能力的客户端；什么都不声明的客户端收到的其余答案都没有变化。在重启前对运行中的宿主实测：935 行，其中 346 行已归档，名册 212,426 字节中的 76,608 字节（36%），已归档父会话的活跃子会话为 0——所以上面的跟随闸门收窄在那台宿主上今天没有任何实例，而省下的字节在每一次列出时都会兑现。
