# Agent Note: Carry the host's questions over the bridge

Status: implemented

## Problem

The remote bridge could not carry `ask_user_question`. The host has had a question service for a while (`ctx.userQuestions`, with a `user-questions/request` waterfall and a `userQuestions` projection), but protocol v1 only exposed `approval.resolve`, which is one tool approval with its own silence-is-refusal rule. A question raised while a phone was connected therefore reached nobody on the phone: the client had no event to render and no method to answer with.

## Decision

- A new capability, `questions.v1`, carries a `question.request` event and a `question.answer` method. Capability-gated exactly like `session.snapshot.page.v1`: a client that does not declare it receives no such event and is refused with `unknown-method`, so its behaviour is unchanged byte for byte.
- The bridge claims the host's `user-questions/request` waterfall in-process, mirroring the existing `approval/request` claim. It claims only while at least one paired client is connected, and it withdraws the claim and calls `next()` when the broadcast reaches no client that declared the capability, so a host answer is never held by a bridge nobody is listening to.
- The claimed request settles differently by state. An `open` question is settled by resolving the waterfall promise the bridge is holding. A `continued` question is forwarded to the host's `answer` remote method, which only accepts continued questions — it looks the call up in `continued(agent)` and returns `false` otherwise, so the open half cannot use it.
- `callId` on the wire is an opaque handle. A timed ask brings the host's real `ToolCallId` in `wait.callId`; a blocking ask brings none, so the bridge mints `bridge:<base64url>`. Without that, every blocking `ask_user_question` — the tool as it is actually declared, with no `timeout` parameter — would be delegated away and no phone would ever see a question.
- An unknown `callId` or a `sessionId` mismatch, and a host refusal that means the question is no longer addressable, are reported as `question-unknown`. Host errors pass through unchanged; the code table stays open.
- The bridge invents no deadline. A timed ask keeps the host's own deadline and becomes `continued` on `ASK_TIMED_OUT`; a blocking ask has no deadline at all and stays `open` until it is answered, the last client leaves, or the bridge is disposed.
- A timed ask now publishes the host's own deadline. The bridge attaches to `userQuestions/attachWait` for a hosted claim, turns the reported `remainingMs` into an absolute epoch-millisecond `expiresAt`, and folds it into the same `question.request` that announces the question; a later frame moves that deadline under the same `callId`, at most once a second. A blocking ask has no host deadline and therefore carries no such key. The subscription is closed on every settling path and at the instant the deadline it reported arrives, because a host parks its own deadline timer while a waiter is attached: letting go is what keeps today's `open` → `continued`.

## Alternatives considered

- **Only claim asks that carry `wait.callId`** (the first implementation). The host type has `wait` optional and only `askTimed` fills it, and the real tool schema declares no `timeout`, so this delegated every genuine question away and made the channel useless for the case it exists for. Rejected.
- **Forward every answer to the host's `answer` method.** That method resolves only continued questions; an open question would fail every time. Rejected.
- **Reuse `approval.resolve` for answers.** It carries a different decision vocabulary and a two-minute silence rule that must not leak onto questions, and the host does not recognise the ids. Rejected.
- **Recompute the questions from session events locally** instead of claiming the waterfall. That would give the bridge a second source of truth for a fact the host already owns, and the projection exists for exactly this. Rejected.
- **Add a local timeout for blocking asks.** The host has none for them; a bridge-invented deadline would fabricate a refusal the user never gave. Rejected.
- **Hold the wait subscription until the claim settles.** The host's `wait.attach` cancels and skips its own deadline timer while a waiter is attached, so a bridge that never let go would suppress `ASK_TIMED_OUT` for as long as a phone was connected and leave the model waiting past its own deadline. Rejected: the subscription is dropped at the reported deadline instead.
- **Read only the first frame and close the stream immediately.** Equal in behaviour today, since the host reports its remaining wait once per attach, and it would need no timer at all. Rejected because that stream is the host's own channel for a deadline that moves; closing it would leave the bridge with no way to relay a later frame short of inventing a second mechanism.
- **Publish a bridge-computed countdown** measured from the moment of the broadcast. That is a deadline of the bridge's own, off by whatever the round trip cost, and it would keep counting after the host had moved on. Rejected.

## Consequences

- A paired phone can now display a pending question and answer it, including one that has already moved to `continued`, where the answer is steered back to the agent as a new turn.
- A blocking question has no deadline, so an unanswered one stays claimable indefinitely. That is the host's own semantics, and such an event carries no `expiresAt` at all: only a timed ask publishes one, and only because the host itself reported it.
- The deadline travels as the host's absolute instant, never as a remaining time the bridge computed, so a phone that sees the same `callId` again replaces the value it holds instead of restarting a clock of its own.
- Verification: the package suite runs 347 tests across 28 files and `pnpm typecheck` is clean; the deadline cases cover the first frame landing in the question's own broadcast, the throttle, a subscription that ends or fails without a frame, the release at the host's deadline, and a claim the host abandons before its first frame. The claim, the minted id, the open/continued split, the `question-unknown` cases, host error pass-through, the withdraw-on-last-client rule and the legacy-client path all have cases.
- Not verified here: an end-to-end run against a real host process. `@deepseek-ai/dsh-user-questions` does not resolve from this package, so the claim is driven by a waterfall-shaped double and the types are declared locally. The round trip needs one manual confirmation.
- The desktop profile resolves this package from `dsh-web/.pinned/dsh-remote-bridge`, a copy rather than the checkout, so rebuilding `packages/dsh-remote-bridge` alone changes nothing the running host can see: copy `lib/` into the pinned package and restart the host. Recorded because it cost a false start on the first device test.
- The listener is registered with `prepend` because the host's waterfall is first-come and the desktop client's own answerer claims every question before this bridge is consulted (a diagnostic at the listener entry proved it never ran). **When a phone that declared the capability is connected, the desktop panel is deliberately not started**: the bridge can settle the host's ask, but it cannot close a panel the host's own UI opened, so starting it would leave a card standing after the phone had already answered. A phone that is absent, and a claim that is withdrawn, still delegate to the rest of the chain.
- A question is broadcast once, at claim time, to the clients that had already declared the channel. A phone that was reconnecting — or whose store was reset by a relaunch — never saw that frame, and the question then sat on the host with an answerable card nowhere. `hello` therefore replays every live claim to the connection that just declared it (`BridgeHub.replayQuestions`, wired in `attach` so every construction path gets it). The claim itself still withdraws when nobody could have received it: a client that cannot hear the frame will not hear it later, and leaving the host's ask held with no card anywhere is worse than delegating.
- Approvals now follow the same shape. `approval.request` is still broadcast once to every paired connection whatever it declared, and `approvals.v1` gates only the second delivery — the replay of still-unsettled claims to a connection that declares it after `hello`. Why the capability gates the replay and not the first broadcast, why it stays out of `SERVED_CAPABILITIES` and off the minor, and how `ApprovalRegistry`'s single settle path keeps a released approval from reviving are recorded in [the protocol note](2026-10-16-remote-bridge-protocol-v1.md); both replays hang off the one `onDeclare` hook, so a connection that declares both capabilities is handed both sets.
