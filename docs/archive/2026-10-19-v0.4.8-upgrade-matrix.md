The blocking finding:

F1. **The row-name repair and the orphan prune are gated on every dsh.profile.bundles entry being resolvable inside the profile's own node_modules, and a profile created by the official CLI never satisfies that.** Such a profile lists @deepseek-ai/dsh-base and @deepseek-ai/dsh-web-app in dsh.profile.bundles but does not install them (the CLI supplies them at boot). liveOverrideIds therefore returns undefined for the first bundle it cannot read, and pruneOrphanOverrides returns before it reaches the repair, silently: the job still settles done. On that shape the update path neither rewrites the stale row names nor prunes the retired override, and the user is left with dead overrides plus the loader line patch: entry "web-ui-model-capabilities" not found on every boot. Measured cause, both directions, in section 5.5. One code path serves all three update routes (gateway.ts:930, :1194 and :1629 all call the same pruneOrphanOverrides, whose first acts are liveOverrideIds and then the repair at :1864), so this is not specific to the CLI writer.

This is a section 0.3 blocking condition in substance: the migration the release relies on is not executed on the update path, and the failure is silent rather than reported. The startup path does repair the names (section 5.4), so a user who restarts reaches a bootable profile with correct row names; the retired override stays, and no path in this release prunes it for a standard CLI profile.

The following limitations are disclosed separately from the gate result and are collected in section 9.

## 4. Scenario A - fresh install at 0.4.8 from the working tree

### 5.5 Cause, measured in both directions

The post-update pass starts at pruneOrphanOverrides (gateway.ts:1853), whose first two acts are composedEntryIdsOf(dump) and liveOverrideIds(composed). liveOverrideIds walks dsh.profile.bundles and returns undefined as soon as one bundle package.json cannot be read, because that bundle own row declarations are then unknown and nothing may be pruned. A CLI-created profile lists the two SDK bundles without installing them:

```
$ node --experimental-transform-types /tmp/dsh-verify-0_4_8-harness/probe-prune-gate.mjs
composedEntryIdsOf -> 109 ids
liveOverrideIds -> undefined (the post-update pass bails out here)
pruneOrphanOverrides -> [] | job.phase: running | job.error: (none)
patch unchanged by the guard: true
  bundle @deepseek-ai/dsh-base -> node_modules present: false
  bundle @deepseek-ai/dsh-web-app -> node_modules present: false
  bundle @linxin666/dsh-web-all -> node_modules present: true
```

The same method, same arguments, on a profile that differs only in that the two SDK bundles are installed into its own node_modules (/tmp/dsh-verify-0_4_8-homeB2, profile upgradeV, 0.4.8 installed, same seeded layer):

```
$ node --experimental-transform-types /tmp/dsh-verify-0_4_8-harness/probe-postupdate-pass.mjs
[plugin-manager] 已修复 profile 中失效的行名：web-ui-task-board（@linxin666/dsh-web-all/task-board → @linxin666/dsh-client-ui-task-board）、web-ui-usage（@linxin666/dsh-web-all/usage → @linxin666/dsh-usage）
pruneOrphanOverrides -> ["web-ui-model-capabilities"] | job.phase: running | job.error: (none)
```

and the resulting composition is clean:

```
$ ... dsh --profile upgradeV --dump-config          # DUMP_EXIT=0

```

That is the whole difference: with the bundles resolvable the pass repairs, prunes and leaves exactly one backup; without them it returns [] and reports nothing. The pass is shared by every update route - the CLI update (gateway.ts:1629), the native update (:1194) and the legacy aggregate migration (:930) - so an in-process writer does not escape it either. The startup repair (index.ts:110) needs only the composition and is unaffected, which is why section 5.4 works.

Not tested: whether a Desktop-owned profile carries those two bundles in its own node_modules and therefore escapes the gate. The live profile is out of scope for this matrix.

### 5.6 The first attempt, and the six-minute CLI budget

The first attempt (job-1, with the profile restored to 0.4.7 afterwards) settled as a job error whose text is the captured CLI output, ending in the pnpm success line:

```
{"job":{"id":"job-1","action":"update","targetVersion":"0.4.8","phase":"error",
 "error":"[check] Lockfile passes supply-chain policies (verified 37s ago)\n...\nPackages: +22 -10\n...\nDone in 576ms using pnpm v11.9.0"}}
package.json after that attempt: "@linxin666/dsh-web-all": "0.4.8"
cordis.patch.yml: unchanged, no backup
```

In that quoted line the CLI's leading check glyph is written as [check], because this repository bans the code point in its own files; the rest of the line is the captured output verbatim.

The gateway kills the CLI child at ADD_TIMEOUT_MS = 6 * 60_000 (gateway.ts:31) and treats any non-zero return as a failed job with the captured output as the message. That the killed child produces a non-zero code rather than a success code is exactly what awaitCliExit does:

```
$ node --experimental-transform-types /tmp/dsh-verify-0_4_8-harness/await-cli-exit-probe.mjs
awaitCliExit(timeoutMs=1000) on "sleep 5" returned code = null | elapsed ms = 1002
code !== 0 interprets as failure: true
```

Consequence for a user, and the reason this is disclosed rather than counted twice: a cold first update that has to download the whole 0.4.8 tree can exceed the gateway six-minute budget on a slow network, and the profile is then left installed at 0.4.8 with the patch untouched. Because the update route refuses when the installed version already equals latest (409), the job cannot be retried in place; recovery needs a return to 0.4.7 and a fresh update, or a restart (which repairs the names) plus a manual removal of the retired override. The second attempt on the same machine, with the store warm, settled done in about ten seconds.

## 7. Scenario D - what each entry point actually does

## 8. Cross-platform honesty

Executed on macOS arm64 (Darwin 25, Node v25.8.1) only.

Covered by execution:

- The full aggregate, including @linxin666/dsh-win-bash@0.4.8, installs on darwin and the row composes with disabled: !!js process.platform !== 'win32'; the loader expression tag evaluates, so the Windows payload is inert here.
- POSIX patch writes (copyFile backup, .tmp, rename, mode 0o600) work, and the chflags-induced rename failure settles as the designed job error.
- The CLI-spawned pnpm path, the native-module installs for cpu-features/ssh2 and the cloudflared postinstall all ran on darwin.
- The gateway six-minute child budget and its non-zero settlement on a killed child were both exercised here.

Platform-sensitive findings, named so a Linux or Windows run knows what to re-check:

- The liveOverrideIds gate (F1) is path-separator dependent: it builds join(profileDir, 'node_modules', ...name.split('/')), so a Windows profile whose bundle resolution differs can only be judged by executing there. Its effect - a silently skipped repair and prune - would reproduce wherever the SDK bundles are absent from the profile tree.
- The chflags un-writable-patch injection is macOS-specific; the equivalent on Linux and Windows (immutable attribute, ACL, read-only file) was not executed, and the error text quoted in section 6.2 is a POSIX EPERM.
- The six-minute CLI budget (section 5.6) is wall-clock, so a slower filesystem or a cold pnpm store widens the window in which an update times out after the install has already landed.
- web-ui-win-bash payload, PATH separator and spawn semantics were never executed on Windows; only the composed row and the installed package were observed on darwin.
